# Prompt Defense: Interview Conductor & Scorer

## Why this system prompt?

The system prompts for **Interview Conductor** and **Interview Scorer** were designed to address three core challenges: 
1. **Flawless JSON Schema Adherence:** By explicitly defining data types within the schema template (e.g., `<integer: 1 to 5>`, `<string: verbatim substring>`) and adding strict constraints against markdown blocks and hallucinations, the prompt forces the LLM to output pure JSON.
2. **Adaptive Logic & Context Forking:** A single prompt must accommodate both `high_wage` (corporate professional) and `low_wage` (entry-level/gig worker) profiles. I explicitly taught the LLM to branch its tone: rigorous and corporate for `high_wage`, vs. accessible, encouraging, and practical for `low_wage`.
3. **Personal, Quality Feedback:** I instructed the model to directly address the user (e.g., "When you said X..."), increasing the perception that the feedback is bespoke rather than generic machine output.

## What did I try first, and what broke?

1. **Vague tone instructions:** Initially, the prompt just passed the `icp_type` (e.g., "low_wage") and relied on the model to infer the tone. 
   - *What broke:* The model asked highly corporate behavioral questions to gig workers (e.g., asking a delivery driver about cross-functional synergy). 
   - *The fix:* Added explicit "Tone & Context Forking" instructions defining exactly what "high_wage" and "low_wage" mean regarding vocabulary and scenario complexity.
2. **Standard JSON instructions without formatting:** Originally, the prompt just said "Output JSON".
   - *What broke:* Claude frequently wrapped the JSON in ````json ... ```` blocks, which crashed the `json.loads` parser. Additionally, `gap_vs_bar` would sometimes output positive numbers even when the user failed the hiring bar, softening the blow.
   - *The fix:* Forced explicit rules: `gap_vs_bar` must be strictly negative if below bar. Added code-level parsing to strip markdown blocks, and improved the prompt schema with explicit type definitions.
3. **Paraphrased quotes:** Initially, I asked for `weak_moment` and `strong_moment`.
   - *What broke:* The LLM would paraphrase what the user said (e.g., "The user mentioned they were flexible"), which failed the strict extraction requirement.
   - *The fix:* Capitalized "EXACT, verbatim substring directly from the text" and added an auto-fail threat in the system prompt if it hallucinated the quote.

## Live Input Change Predictions

During a demo call, changing input variables will directly impact the output due to the adaptive logic:

1. **Changing `company_tier` (e.g., 'startup' -> 'enterprise' for a high_wage engineer):** 
   - *What changes:* The Conductor's questions will pivot from asking about wearing multiple hats or shipping fast (startup traits) to asking about scalability, rigid CI/CD pipelines, and navigating large cross-functional teams (enterprise traits).
2. **Changing `language` (e.g., 'en' -> 'hi' for a high_wage profile):** 
   - *What changes:* The Conductor will output questions in Hindi. However, because it is `high_wage` and technical, it will likely use a mix of Hindi and English tech jargon (Hinglish), keeping terms like "System Design" or "Microservices" in English while using Hindi for the conversational wrapper.
3. **Changing `round_type` (e.g., 'technical' -> 'behavioral'):**
   - *What changes:* The first question generated by the Conductor will no longer probe technical stack skills, but rather conflict resolution, leadership, or past experiences.
4. **Providing a weak technical answer (Live input test):** 
   - *What changes:* The Conductor's next turn will explicitly output a lower `difficulty_level` (e.g., moving from 4 to 2) and the `reasoning` will state: "Because the candidate failed to explain X, I am asking a simpler follow-up on fundamental concept Y." The Scorer's `gap_vs_bar` for technical will become highly negative.
